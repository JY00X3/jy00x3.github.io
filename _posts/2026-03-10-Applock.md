# 🔓 Android AppLock Pattern Cracking Deep Dive

![Desktop View](/assets/applock/1.png){: width="700" height="400" .normal }

In this walkthrough, we analyze how an Android **AppLock application stores its pattern lock** and demonstrate how to recover the original pattern through **reverse engineering and brute forcing**.

Many Android AppLock applications rely on **locally stored hashes**, which can become an attack surface when extracted from the device.

In this lab we will:

- Analyze the application's **AndroidManifest**
- Inspect **SharedPreferences storage**
- Identify the **pattern encryption method**
- Extract the stored pattern hash
- Recover the **original unlock pattern**

---

# 🧠 Application Overview

AppLock applications are designed to **protect apps or files using a pattern lock**.

However, if the application stores the lock pattern locally without strong protection, it becomes possible to retrieve and crack it.

Our target application stores its configuration inside:

```
SharedPreferences
```

Which is common for Android applications.

---

# 📦 Manifest Analysis

The **AndroidManifest.xml** reveals several permissions and exported components.

# 💾 SharedPreferences Analysis

Next we inspect the application's **SharedPreferences**.

![Desktop View](/assets/applock/2.png){: width="700" height="400" .normal }

Inside the configuration file we discover the stored pattern value:

```xml
<string name="image_lock_pattern">2wTGRwcsTKXnuFMR4DEIRZrSt0k=</string>
```

This string represents the **stored pattern lock**.

At first glance it looks like **Base64 encoded data**.

---

# 🔍 Code Investigation

Searching the codebase for the key:

```
image_lock_pattern
```

leads us to the implementation responsible for pattern validation.

![Desktop View](/assets/applock/3.png){: width="700" height="400" .normal }

The code shows the following behavior:

1. The pattern is hashed using **SHA‑1**

![Desktop View](/assets/applock/5.png){: width="700" height="400" .normal }

![Desktop View](/assets/applock/4.png){: width="700" height="400" .normal }

2. The resulting hash is **Base64 encoded**

3. The encoded value is stored inside **SharedPreferences**

Flow:

```shell
User Pattern
      ↓
SHA‑1 Hash
      ↓
Base64 Encoding
      ↓
Stored in SharedPreferences
```

Example stored value:

```shell
2wTGRwcsTKXnuFMR4DEIRZrSt0k=
```

---

# 🧩 Attack Strategy

Since the pattern is:

- SHA‑1 hashed
- Then Base64 encoded

We can attempt a **brute-force attack** against all possible Android lock patterns.

Fortunately, Android pattern locks have a **limited keyspace**, making brute forcing feasible.

To automate this, we use the tool:

```shell
https://github.com/sch3m4/androidpatternlock
```

---

# 🔧 Preparing the Hash

First we decode the stored value from Base64.

```bash
echo "2wTGRwcsTKXnuFMR4DEIRZrSt0k=" | base64 -d > pat.key
```

This creates the file:

```shell
pat.key
```

Which contains the **raw SHA‑1 hash**.

---

# 💻 Running the Brute Force Script

Next we run the cracking tool:

```bash
python2 aplc.py pat.key
```

The script will:

1. Generate all valid Android patterns
2. Hash them with SHA‑1
3. Compare against the extracted hash

Once a match is found, the **original pattern is revealed**.

![Desktop View](/assets/applock/6.png){: width="700" height="400" .normal }

# ⚠️ Why This Works

The vulnerability exists because:

- Pattern hashes are stored **locally**
- **No salting** is used
- The pattern space is **small**
- **No rate limiting** exists

This allows offline brute-force attacks.

---

# 🛡️ Defensive Perspective

To protect against this type of attack, developers should implement:

### Stronger Storage

- Use **salted hashes**
- Use **Android Keystore**

### Secure Authentication

- Hardware-backed keystore
- Biometric authentication
- Encrypted storage

> **Client-side protections are only as strong as their storage mechanisms.**
